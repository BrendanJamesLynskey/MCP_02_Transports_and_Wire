Why MCP Needs More Than One Transport

The protocol is transport-agnostic by design — the JSON-RPC envelopes don't care how they got there. But the practical deployments split cleanly into two worlds with different constraints, and the spec ships first-class transports for each.

Local servers — stdio

Spawned as a child process by the host. No network exposure. No auth. The host's user trust transfers directly. This is how 90% of community servers ship.

Examples: filesystem, git, sqlite, any server you uvx or npx from the command line.

Remote servers — Streamable HTTP

One server, many clients across the public internet. Needs auth (OAuth 2.1), session management, reconnection, multiplexing. Originally HTTP+SSE; superseded by Streamable HTTP in 2025-03-26.

Examples: a hosted Linear server, a SaaS observability server, anything you point at over https://.

Custom transports are allowed

The spec explicitly says implementations MAY add their own transports (named pipes, WebSockets, gRPC) provided they preserve JSON-RPC semantics, message ordering and the lifecycle. But anything custom-built breaks interop with mainstream hosts — in practice, ship one of the two standard transports.

02

stdio — The Default for Local Servers

The host launches the server as a subprocess and pipes stdin/stdout. That's it. Each side reads JSON-RPC messages from one stream and writes to the other.

Framing rules — line-delimited JSON

  • Each message is a single JSON object on a single line, terminated with \n (LF). No embedded newlines — if your JSON is pretty-printed, you've corrupted the stream.
  • STDOUT carries protocol only. One stray print() call in your server will desynchronise the client's parser.
  • STDERR carries logs only. The host MAY display it for debugging, but it must not contain JSON-RPC messages.
  • Encoding is UTF-8. Messages must not contain embedded NULs.
  • Since 2025-06-18, JSON-RPC batches (a top-level array) are no longer permitted on any transport, including stdio.
Two messages on stdio (each one literal line)
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"x","version":"0"}}}
{"jsonrpc":"2.0","method":"notifications/initialized"}

How the host configures stdio servers

The host's config typically maps a name to a command line and an environment. Claude Desktop's claude_desktop_config.json is representative:

claude_desktop_config.json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/Users/me/projects"],
      "env": { "DEBUG": "1" }
    },
    "sqlite": {
      "command": "uvx",
      "args": ["mcp-server-sqlite", "--db-path", "/tmp/test.db"]
    }
  }
}
Common bug: blocked stdout

If your server writes to stdout faster than the host reads, the OS pipe buffer fills (typically 64 KiB on Linux) and your write() blocks forever. Servers that emit large resource bodies should chunk and yield. The MCP Inspector is invaluable here — it shows the stall as a hung request.

HTTP+SSE (Legacy) — What It Did and Why It Died

The original web transport, shipped with 2024-11-05 and deprecated in 2025-03-26. Worth understanding because (a) servers in the wild still use it and (b) it explains the design pressure that produced Streamable HTTP.

Two endpoints, two directions

Client
→
POST /messages
→
Server
Client
←
GET /sse (text/event-stream, long-lived)
←
Server

The first message on /sse was a synthetic endpoint event telling the client which URL to POST to. Every subsequent server-to-client message arrived as an SSE data: event on the same stream.

A snippet of the SSE stream
event: endpoint
data: /messages?session_id=8c8a7b...

event: message
data: {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2024-11-05",...}}

event: message
data: {"jsonrpc":"2.0","method":"notifications/tools/list_changed"}

Why it died

  • Two endpoints meant two failure modes. If the SSE socket dropped while a POST was in flight, the response could never reach the client.
  • No clean resumability. Reconnecting /sse meant losing every message between the disconnect and the reconnect.
  • Awkward for stateless infra. Load balancers that serialise on session IDs need a single canonical URL, not a flow that bounces between two paths.
  • SSE's request/response asymmetry made it impossible for a single POST to receive a streamed response (e.g. progress notifications during a long tool call).
04

Streamable HTTP — Single Endpoint, Two Modes

Introduced in 2025-03-26. One URL, typically /mcp or /, that accepts both POST and GET. The server picks per request whether to respond with a single JSON body or to upgrade to an SSE stream.

MethodBodyServer responseUsed for
POST /mcpOne JSON-RPC request or notification200 with application/json (single response) or 200 with text/event-stream (streamed response + intermediate notifications) or 202 Accepted (notification-only, no body)Every client-initiated message
GET /mcp(none)200 with text/event-stream — pure server-to-client channel for unsolicited notifications. 405 Method Not Allowed if the server doesn't support server-initiated streams.Long-lived listening channel
DELETE /mcp(none, with Mcp-Session-Id)204 No Content — terminates the sessionClean session shutdown

Why two response modes for one POST?

The same call can need either shape. tools/list takes microseconds and returns a single JSON object. tools/call on a long-running operation may want to emit notifications/progress for two minutes before returning the final tool result. The server signals which mode by setting the Content-Type header on the response.

POST returning a streamed multi-message response
POST /mcp HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbG...
MCP-Protocol-Version: 2025-06-18
Mcp-Session-Id: 1d31a3f4-...
Accept: application/json, text/event-stream
Content-Type: application/json

{"jsonrpc":"2.0","id":42,"method":"tools/call",
 "params":{"name":"long_query","arguments":{"sql":"..."}}}

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

event: message
id: 1
data: {"jsonrpc":"2.0","method":"notifications/progress",
       "params":{"progressToken":"abc","progress":0.25}}

event: message
id: 2
data: {"jsonrpc":"2.0","method":"notifications/progress",
       "params":{"progressToken":"abc","progress":0.75}}

event: message
id: 3
data: {"jsonrpc":"2.0","id":42,"result":{...}}
The Accept header is mandatory

Clients MUST send Accept: application/json, text/event-stream on every POST. Servers reject any other Accept with 400. This is what tells a stateless reverse-proxy that the response could be either shape and to disable buffering accordingly.

05

Sessions and the Mcp-Session-Id Header

Sessions are optional but standardised. A server that wants to remember client state across requests opts in by returning Mcp-Session-Id on the initialize response.

step 1
POST /mcp { method: "initialize", ... }
step 2
200 OK Mcp-Session-Id: 1d31a3f4-c1d4-4e9c-9e10-...
step 3+
POST /mcp Mcp-Session-Id: 1d31a3f4-... { method: "tools/call", ... }
end
DELETE /mcp Mcp-Session-Id: 1d31a3f4-... → 204

Server-side state semantics

  • The session ID MUST be a globally unique, cryptographically random value — not a sequential counter.
  • If the server has invalidated the session (timeout, redeploy, eviction), it returns 404 Not Found on requests carrying that ID. The client MUST then re-initialize.
  • The session is the canonical place to attach: capability negotiation results, the agreed protocol version, the OAuth principal, scratch caches, subscription lists.
  • For horizontally-scaled servers, sticky-routing on this header is the simplest correct approach — or store session state in shared infrastructure.
Stateless servers are allowed too

If your server has no per-session state (it's a thin shim over an idempotent HTTP API, say) you can simply not return Mcp-Session-Id at all. Every request is then standalone — the client just won't bother sending one back. This is the easiest deployment shape if your model fits.

06

Resumable Streams — Last-Event-ID in Practice

SSE has had a built-in resumption mechanism since HTML5: when the browser reconnects to a stream, it sends the last id: it saw in the Last-Event-ID request header. The server then replays everything after that ID. MCP exploits this directly.

Implementation note

Replay buffers don't need to be unbounded. A reasonable server keeps the last N events (say 1000) per session and replays from there; if Last-Event-ID is older than the buffer, return a fresh stream and let the client re-issue the affected request. The client SHOULD treat any in-flight request as “result unknown” on disconnect and decide whether to retry based on whether the tool was idempotent.

Auth, Origin, and the DNS-Rebinding Trap

Three headers carry all the security weight at the transport boundary:

HeaderRequiredPurpose
Authorization: Bearer <token>Remote serversOAuth 2.1 access token. Validated per-request against the issuer's metadata. Audience MUST match this server's URL (RFC 8707).
MCP-Protocol-VersionAll HTTP requests after initializeEchoes the negotiated protocol version. A mismatch SHOULD be rejected with 400.
OriginLocalhost servers binding HTTPValidates that the request came from a permitted origin — not a malicious page that lured a browser into resolving evil.com to 127.0.0.1.

The DNS-rebinding attack on local HTTP servers

A surprising number of MCP servers expose Streamable HTTP on http://127.0.0.1:PORT for development. Without an Origin check, any web page the user visits can issue fetch() calls against that loopback port using DNS rebinding (resolve attacker.com first to a public IP, then to 127.0.0.1). The result: a webpage drains your tokens.

The two checks every loopback HTTP server MUST do
// 1. Bind explicitly to loopback, not 0.0.0.0
server.listen(PORT, "127.0.0.1");

// 2. Reject requests with foreign Origin
const ALLOWED = new Set(["http://localhost", "app://obsidian.md", ...]);
app.use((req, res, next) => {
  const origin = req.headers.origin;
  if (origin && !ALLOWED.has(new URL(origin).origin))
    return res.status(403).end();
  next();
});
Why the spec calls this out

The Origin header is one of the few HTTP headers that the browser refuses to let JavaScript override. That's why it's the right gate: it pins down the actual page that initiated the request, even after a DNS rebind. Deck 04 (Security) goes deeper on the wider OAuth threat model.

Choosing a Transport in 2026

Use stdio when…

  • The server runs locally beside the host
  • You don't want to deal with auth at all
  • Distribution is via uvx / npx / a binary in the user's PATH
  • Resource lifetime equals the host's session

Use Streamable HTTP when…

  • The server is hosted as a service
  • One server instance backs many users
  • You need OAuth (you almost always do)
  • Long-running tools need to push progress
  • You want resumable sessions across reconnects

Migrating off HTTP+SSE

If you ship an HTTP+SSE server today, the migration is incremental:

  1. Keep the old POST /messages + GET /sse endpoints alive for one major version of your client.
  2. Add the unified /mcp endpoint that speaks Streamable HTTP.
  3. Advertise the new endpoint via your service-discovery channel (homepage, well-known, README).
  4. Drop the old endpoints once usage falls below your retention threshold.
Take-aways

stdio is JSON-on-newlines. Don't print to stdout. Don't batch. Don't embed newlines.

Streamable HTTP is one URL, two response shapes. The server picks per request between a flat JSON response and an SSE stream.

Sessions are an opt-in header and the right place to anchor protocol version, capabilities, OAuth principal and per-stream replay buffers.

Resumability is free if you tag SSE events with monotonic IDs and keep a bounded replay buffer.

Origin and audience are the two checks that stop the easy attacks — covered in detail in deck 04.
